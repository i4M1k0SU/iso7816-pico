# 内部構造と実装メモ

## 動作原理

```
         reader CLK (C3) ──┐
                           ▼
  PIO SM0 (rx) : wait 1 pin → wait 0 pin (start) → CLK エッジを数えて 0.5 ETU → 9 bit を bit 中央でサンプル → FIFO
  PIO SM1 (tx) : FIFO から 1 bit ずつ out pindirs (1 = Low 駆動, 0 = 解放) → CLK を F/D 回数えて 1 ETU
```

* ETU はリーダーのクロックをそのまま数えて生成する (`wait 0 gpio` / `wait 1 gpio` ループ)。
  クロック周波数の測定や sysclk からの分周は不要で、リーダーが何 MHz を出しても追従する。
  受信側の半 ETU 待ちは CLK の **エッジ** を数えるため、F/D=372/4 の 93 クロックのような奇数 ETU でもサンプル位置が正確である。
* I/O は `out pindirs` でオープンドレインを実現する。送信中は自分の文字を RX が読み戻すので、
  それを送信完了の検出と衝突検知に使用する。
* T=0 ではエラー信号と文字の繰り返しを両方向で行う (T=1 では行わない)。リーダーからの文字にパリティ誤りがあれば
  エラー信号を返して再送させ、自分の文字にリーダーがエラー信号を返せば同じ文字を送り直す。詳細は次の
  「T=0 のエラー信号と文字の繰り返し」に記す。
* RST の立ち下がりは GPIO 割り込みでラッチし、短いリセットパルスも取りこぼさない。
  この割り込みは `gpio_add_raw_irq_handler()` で登録した共有の raw ハンドラであり、RST のイベントだけを見て確認応答する。
  SDK の唯一の GPIO コールバック (`gpio_set_irq_callback()`) は占有しないので、アプレットやフックが他の GPIO の割り込みを併用できる。
  RST が High になると TX の OSR に 1 フレーム分の「解放」を仕込んでから起動するので、ちょうど 12 ETU 後に ATR が始まる
  (規格の 400〜40000 クロックの範囲内)。CLK 周波数は pio1 の `clkcount` プログラムで
  500 us 間の立ち上がりエッジを数えて実測する (`wait pin` はパッド入力を読むので、CLK はどの GPIO でもよく、ピン機能は pio0 のまま)。
* リーダーから受けた文字の後、応答は先頭エッジ間隔が 16 ETU (T=1 は BGT 22 ETU) になるまで待ってから送る。
  これを守らないとリーダーが応答を取りこぼす。
* 起動時にループバック自己診断を行う: 空きピン `ISO7816_SELFTEST_PIN_CLK` (既定 GP16) にシステムクロックの 1/32
  (125 MHz なら 3.9 MHz) の試験クロックを PIO で出し、`ISO7816_SELFTEST_PIN_IO` (既定 GP17) を I/O として ATR の送受信と
  ETU の実測、さらに F/D=372/4 + 逆規約での送受信を行い、結果をコンソールに表示する。どちらかを -1 にすると行わない。
* PIO はシステムクロックで動き、リーダーの CLK を `wait gpio` で数える (1 周期あたり最大 4 命令、ビット境界でさらに
  5 命令)。ETU を正確に数えるにはシステムクロックが CLK の 8 倍以上 (`PHY_MIN_SYSCLK_PER_CLK`) 必要で、下回ると
  セッション開始時に警告を出す。125 MHz なら CLK 15 MHz 程度、48 MHz なら 6 MHz 程度のリーダーまで追従できる。

## T=0 のエラー信号と文字の繰り返し

ISO 7816-3 7.3 により、T=0 の受信側はパリティ誤りの文字に対し、その先頭エッジから 10.5 ± 0.2 ETU に 1〜2 ETU の間
I/O を Low にする (エラー信号)。送信側は 11 ± 0.2 ETU で I/O を調べ、Low なら少なくとも 2 ETU 後に同じ文字を送り直す。
T=1 にはこの仕組みがなく、誤りはブロックの EDC で検出してブロック単位で再送する。

### 送信 (カード → リーダー)

`phy_tx()` は `error_signal` (T=0) のとき 1 文字ずつ送る。各文字のエコー (9.5 ETU) を受けてから 12 ETU まで I/O を
監視し、次の文字はその後に送る。文字間隔は 12 ETU + 数 µs になる (SCR3310、372/1 で実測 12.1 ETU)。
エラー信号の判定は CPU のポーリングに頼らず受信ステートマシンを使う。受信機はエコーを push した後 `wait 1 pin` /
`wait 0 pin` でスタートビットを待っており、ガードタイム中の立ち下がりを見るとそこから 9.5 ETU の間はこの 2 命令の外にいる。
12 ETU の時点でプログラムカウンタがこの 2 命令以外にある (または受信 FIFO に語がある) なら、エラー信号が来たとみなす。
したがって割り込みで CPU の確認が数 ETU 遅れても検出できる。CPU のポーリングは開始と終了の時刻をトレースに残すために使う。
検出したら I/O が High に戻るのを待ち、その 2 ETU 後に受信機を再起動して (エラー信号を読みかけた偽の文字を捨てる)
同じ文字を送り直す。1 文字につき 4 回繰り返しても拒否されれば `phy_tx()` は失敗する
(`tx: character rejected by the reader (error signal)`)。T=1 では従来どおり 8 段の TX FIFO に詰めて連続で送る。
繰り返した回数は `status` の `repetition` に出る。

以前の実装は T=0 でも連続送信で、リーダーのエラー信号を扱わなかった。そのため受信機がエラー信号の立ち下がりを
スタートビットと取り違え、その偽の語を次の文字のエコーとして数えていた。SCR3310 で応答の SW1 のパリティを
わざと誤らせると、エコー誤りが 1 回数えられ、SCardTransmit は SCARD_E_COMM_DATA_LOST (0x8010002F) で失敗した。

コンソールの `txperr <index> [count]` は、セッションの index 番目の送信文字 (ATR の TS = 0 から数え、繰り返しは数えない)
を count 回だけパリティを反転して送る。`trace` の `P` がその送信、`E` / `e` がリーダーのエラー信号の開始 / 終了
(自分の文字の先頭エッジからの 1/10 ETU) である。SCR3310 (4.8 MHz、Windows の CCID ドライバー) での結果は次のとおり。

| 誤らせた文字 | リーダーの反応 |
|-------------|---------------|
| ATR の 3 文字目 | エラー信号を出さず、そのまま ATR を受け入れる (ATR 中の文字の繰り返しは規格上任意) |
| PPS 応答の PPS1 (372/1) | エラー信号 (`E 068` = 10.4 ETU から)。繰り返した文字を受け入れ、PPS は成立する |
| T=0 応答の SW1 / SW2 (372/1) | エラー信号 (10.4〜10.5 ETU から約 1.5 ETU)。4 回続けて拒否させても 5 回目を受け入れる |
| T=0 応答の SW2 (372/4、1 ETU = 19.4 µs) | 同じくエラー信号を出し、繰り返しを受け入れる |
| T=1 の S(IFS response) の INF | エラー信号は出さない。約 22 ms 後に S(IFS request) を送り直し、セッションは回復する |

### 受信 (リーダー → カード)

`rx_pop()` はパリティ誤りの語を取り出したときにエラー信号のフレーム (1 ETU 解放、2 ETU Low) を送る。信号は取り出した
時刻から数えるので、受信機の push (9.5 ETU) から取り出しまでの遅れ δ がそのまま信号の遅れになる。δ が大きいと信号は
リーダーの 11 ETU の確認に間に合わず、リーダーが続けて送る文字に重なる。そこで `rx_pop()` は「最後に FIFO が空だった時刻
から今まで」を δ の上限とし、それが 0.3 ETU (`ERROR_SIGNAL_MAX_LATE_TENTHS`) を超えるか FIFO に 2 語以上あれば、
エラー信号を出さずに文字を捨てる (どちらにしても文字は失われ、T=0 では WWT の期限切れから立ち直る)。
`status` の `rx latency` に δ の上限の最大値と、遅すぎた文字の数が出る。

SCR3310 での実測 (δ の上限、コンソール接続中でログを送りながら `tools/sc_test.ps1` を実行):

| 条件 | 文字数 | ≤ 0.1 ETU | ≤ 0.3 ETU | ≤ 1 ETU | 最大 |
|------|--------|-----------|-----------|---------|------|
| T=0, 372/1 (1 ETU = 77 µs) | 1106 | 1106 | 0 | 0 | 5 µs |
| T=0, 372/4 (1 ETU = 19.4 µs, PPS) | 1090 | 1005 | 84 | 1 | 18 µs |
| T=0 特定モード, 372/4 | 2211 | 2037 | 174 | 0 | 5 µs |
| T=1, 372/1 | 4051 | 4051 | 0 | 0 | 5 µs |

遅れはコマンドの 1 バイト目を待つ間のアイドル処理 (コンソール、ログ送出) から来る。372/1 では問題にならず、
372/4 でもまれである。受信 FIFO の割り込みでエラー信号を出す方式も考えられるが、エコーの読み出しと FIFO を共有する
作りの変更に見合わないので採らない。

### 転送パラメータの切り替え

`phy_apply_params()` は、直前に送った文字のフレーム (12 + N ETU) が終わるまで待ってからステートマシンを止める。
以前は `phy_tx()` が最後のエコー (9.5 ETU) で戻った直後に止めうる作りで、パリティビットが 0 の文字 (PPS 応答の
PCK FC など) では Low のまま止まり、再設定まで線を引き続ける危険があった。実測では PPS の後の呼び出しは最後のエコーから
82〜86 µs (372/1 で約 1.1 ETU、フレームの 10.6 ETU) で、ログ出力を挟むおかげでパリティビットの後になっていた
(余裕は約 0.6 ETU)。ETU とガードタイムが変わらない場合 (PPS で F/D を変えない、プロトコルだけ変わる) は
ステートマシンに触れず、CPU 側のパラメータだけを替える。

## セッションの流れ

1. RST High → `phy_start_session()` (既定 F/D、規約は ATR から) → ATR 送出。
2. 最初の受信バイトが FF なら PPS。応答後に `phy_apply_params()` で F/D とプロトコルを切り替える。
   ATR が特定モード (TA2 あり) なら PPS には応じず、ATR 送出の直後に `phy_apply_params()` で TA1 の F/D へ切り替える。
3. `session.c` が T=0 (`t0.c`) または T=1 (`t1.c`) のコマンドループを回す。
4. 両トランスポートは完全な APDU を組み立てて `dispatch_process()` に渡し、SW と応答データを受け取る。
5. コマンド待ちのアイドル処理 (`phy_rx()` の `idle` 引数で呼ばれる `idle_service()`) は、NVM が dirty で文字の送受信が
   `NVM_IDLE_SAVE_MS` (200 ms) 途絶えていれば保存する。T=1 では保存中 (50-100 ms、割り込み停止) に届いたブロックが
   8 段の受信 FIFO からあふれうるが、リーダーの再送で回復する。あふれは `status` の `rx overrun` とログ
   (`PHY: RX FIFO overrun`) に出る。PIN / PUK の試行回数は `sec.c` が照合前に同期で保存する。
6. RST Low で `phy_enter_reset()`、NVM がまだ dirty なら保存 (内容が変わっていなければ書かない。スロット方式の詳細は
   [card-profile.md](card-profile.md) の「永続データ」)。

### T=0 の ENVELOPE の終端

T=0 では拡張長 APDU を ENVELOPE (INS C2) に分けて送る。ISO 7816-4 は ENVELOPE の連鎖がどこで終わるかを定めていないため、
`t0.c` (`handle_envelope()`) は次の規約を採る。

* Lc (P3) = 255 の ENVELOPE は「続きがある」を意味し、データを蓄積して 9000 を返す。
* Lc が 255 未満の ENVELOPE (Lc = 0、つまり P3 = 00 を含む) が最後の片である。蓄積したバイト列全体を 1 つの APDU として
  解読して実行し、解読できなければ 6A80、蓄積が `APDU_BUF_SIZE` を超えれば 6700 を返して連鎖を破棄する。
* したがって APDU の全長が 255 の倍数になるホストは、最後にデータなしの ENVELOPE (`xx C2 00 00 00`) を送らなければならない。
* ENVELOPE の TPDU 自体はケース 3 であり、リーダーはデータを送り終えて SW1 SW2 だけを待っている。そのため内側の APDU が
  応答データを返す場合は、内側がケース 2 (Lc なし) でもケース 4 でも、また Le の値にかかわらず、必ず 61xx で知らせて
  GET RESPONSE で取り出させる。ENVELOPE に 2 度目の ACK とデータを返したり 6Cxx を返したりはしない。応答データがなければ
  SW だけを返す。

### T=0 の受信タイムアウト

ヘッダーの 2 バイト目以降と、ACK の後のデータ部は、リーダーが続けて送ってくるバイトである。`t0.c` はこれらを
1 バイトごとに WWT = 960 × D × WI ETU の期限付きで受信する。WI は ATR の TC2 (なければ 10) で、`session.c` が
`t0_set_wi()` で渡す。D は PPS 後の現在値である。期限が切れたら途中までの TPDU を捨ててログに残し、次のヘッダーを待つ。
これがないと、ノイズや迷った 1 文字が CLA とみなされて以後のヘッダーが 1 バイトずつずれ、カードは来ない 5 バイト目を
待ち続け、リーダーは WWT 後にリセットする (Windows ではカードが mute 扱いになることがある)。ヘッダーの 1 バイト目は
期限なしで待つ。途中で切れた ENVELOPE のデータは連鎖全体を破棄する。

応答データのないケース 2 コマンド (ハンドラーが Nr = 0 で 9000 などを返す) には ACK を送らず SW1 SW2 だけを返す。6Cxx は
La > 0 を知らせるものであり (6C00 は La = 256 を意味する)、Nr = 0 には使えない。

### T=1 の誤り処理

`t1.c` は ISO/IEC 7816-3 11.6.3 の誤り処理に従い、次のように振る舞う。

* 不正なブロック (EDC 誤り、LEN = FF、ブロック途中の CWT 超過) には、期待する I ブロックの番号を N(R) に入れた
  R ブロックを返す (EDC 誤りは誤りコード 1、それ以外は 2)。応答の前に、リーダーが CWT の間黙るまで受信文字を読み捨てる。
  LEN の化けたブロックの残り (最大 256 文字) と衝突したり、それを別のブロックとして解釈して R ブロックを連発したりしないためである。
  CWT = (11 + 2^CWI) ETU で、CWI は ATR の TB3 (なければ 13) から取り、余裕として 1 ETU あたり 1 µs と 1 ms を足す。
* 再送用に保持するのは、最後に送った I ブロック (リーダーの次の I ブロックで確認されるまで) と、リーダーのチェイニングに
  対する確認応答の R ブロックだけである。誤りを知らせる R ブロックと S ブロックは保持しない。保持すると、そのあとの
  再送要求 R(N(R)) に I ブロックではなく R ブロックを返し続けることになる。
* 再送要求またはリーダーの I ブロックの繰り返しに対して保持しているブロックがなければ (ATR 直後、RESYNCH / ABORT の後)、
  R(N(R)) を誤りコード 2 で返す。黙るとリーダーは BWT まで待たされる。
* リーダーのチェイニングの途中で I ブロックが繰り返されるか R ブロックが届けば、同じ確認応答を返し直す (データは二重に蓄積しない)。
* コマンドのチェイニングが `APDU_BUF_SIZE` を超えても、カードから S(ABORT) は送らない。Windows の usbccid をはじめ
  TPDU レベルのリーダーの多くはカード起点の ABORT を扱えないためである。残りのブロックも R ブロックで確認応答しつつ
  データを捨て、チェインの最後の I ブロックに 6700 を返す。リーダー起点の S(ABORT) には従来どおり応答する。
* S(IFS request) は IFSD 01..FE を受け付ける (00 と FF は予約)。S(RESYNCH) は順序番号、チェイニングの状態、再送用の
  ブロックを捨て、IFSD を初期値 32 に戻す。カードが要求していない S(... response) は不正なブロックとして R ブロックで答える。
* ATR 直後、正しいブロックをまだ 1 つも受けていないうちの R ブロックは NAD = 0 で送る (前のセッションの NAD を使わない)。
* BWI (TB3 の上位) は使わない。カードは BWT を数える側ではなく、長い処理は `card_keepalive()` の S(WTX) でリーダーを待たせる。

## ディスパッチの順序

1. CLA 解読 (チャネル、チェイニング、SM)。閉じたチャネルは 6881。
2. SM bit があれば `hooks.sm_unwrap`。
3. チェイニング中なら蓄積して 9000 を返し、最後の片で全体を処理する。
4. SELECT by DF name → アプレット (前方一致、`select` が 9000 / 62xx / 63xx を返したときだけ選択成立)、
   なければファイルシステムの DF。
5. MANAGE CHANNEL (開いたチャネルでもアプレットの `select` を呼ぶ)。
6. チャネルのアプレット: コマンド表のハンドラ → `process`。
7. `iso_commands` が真かつ CLA が interindustry なら標準コマンド表。
8. `hooks.unhandled`。
9. interindustry の GET RESPONSE は 6985。他は 6E00 (現在の文脈で、その INS のハンドラが別の CLA にある) または 6D00。
10. SM bit があれば `hooks.sm_wrap`。

## はまりどころ

* RP2040 / RP2350 の PIO 命令メモリは **書き込み専用** (読むと 0)。`wait gpio` のピン番号を差し替えるときは
  プログラム配列の元の命令を加工して書き込む必要がある。
* autopull 有効時に `out null, 32` を `pio_sm_exec` で強制実行して OSR を空にすると、その命令が autopull 待ちで止まったままになり、
  次に FIFO へ入れた 1 ワードを飲み込む。代わりに `mov osr, null` で 0 を 1 フレーム分詰めておき、
  それを「ATR 前の 12 ETU 待ち」として使用する。
* `FDEBUG.TXSTALL` は送信完了の検出には使用できない。送信完了は自分の文字のエコーで判定する。
* 受信プログラムは文字ごとに `push block` で終わるので、FIFO (8 段) が満杯だとそこで止まり、その間の I/O を見ていない。
  落ちた文字は後でパリティ誤りや EDC 誤りとしてしか現れないため、`rx_pop()` が `FDEBUG.RXSTALL` (SM0 のビット) を
  見て `rx_overruns` を数え、1 を書いて消す。セッション開始時 (`sm_configure()`) にも消しておく。
* SM0 / SM1 は番号を固定して使うので `phy_init()` が `pio_sm_claim()` で確保する。確保しないと、アプリケーションの
  `pio_claim_unused_sm(pio0, ...)` が SM0 を返して受信機を書き換えてしまう。
* RX (25 命令) と TX (5 命令) で pio0 がほぼ埋まるため、CLK 計測用のカウンタ (`clkcount`, 常駐) と
  自己診断用のクロック生成 (`clkgen`, 自己診断中のみ) は pio1 に置く。
* Windows は ATR を返さなかったカードを「無応答 (mute)」として記憶し、以後の `SCardConnect` はリーダーに触れずに即座に失敗する
  (カードを抜き差しするまで)。`SCARD_SHARE_DIRECT` で接続してから `SCardReconnect(SCARD_RESET_CARD)` を呼ぶと再活性化する
  (`tools/sc_test.ps1` に組み込み済み)。
* CLA 8X..FX (proprietary class) のチェイニング / チャネル bit は既定では解釈しない。解釈すると CLA 90 が「80 のチェイニング」になり、
  独自 CLA が潰れる。

## 既知の制限

* クロック停止 (clock stop)、T=1 の CRC、ERASE BINARY/RECORD、ENABLE/DISABLE VERIFICATION、
  受信パリティ誤り時のエラー信号 (リーダー → カード) は実装済みだが SCR3310 では発生させられず未検証である
  (ループバック自己診断では確認している)。
* カードは WWT (T=0) / BWT (T=1) を自分では守らない。ハンドラーが WWT (既定 960 × 10 ETU、372/1 で約 0.74 s) や BWT を
  超えて処理するときは `card_keepalive()` を呼ぶ必要があり、呼ばなければリーダーはタイムアウトしてカードをリセットする。
* セキュアメッセージング、ISO 7816-8 の暗号コマンド、CREATE/DELETE FILE はフックのみ (本体はユーザー実装)。
* ファイルの木は静的 (ソース上の表)。実行時にファイルを作るには `create_file` フックと自前の領域管理が必要である。
* 論理チャネルは基本符号化の 0..3 (最大 4 チャネル) に対応する。拡張符号化 (CLA 4X..7X) は解読のみ。
